## 1. DSH architecture and extension model (claimed)

- DSH is described as built on the **Cordis framework**, "everything is a plugin"; the active tool set is
  composed from an agent preset file, and each profile has a patch file that configures or toggles plugins.
- Cordis plugin contract shown: `export const name`, `export const inject = ['fs', 'tools']`,
  `export function apply(ctx: Context)`.
- Package / identifier names asserted (none verified): `@deepseek-ai/dsh`, `@deepseek-ai/cordis`,
  `@deepseek-ai/dsh-tools` (`defineTool`), `@deepseek-ai/dsh-fs`, `@deepseek-ai/dsh-tool-git`,
  `dsh-hook-protocol` (with a `hooks.json` mapping), `fs-observation-policy`.
- Example preset path given: `presets/standard.patch.yml`.
- Preset-patch shape proposed for removing a tool entirely:

  ```yaml
  id: preset-standard
  config:
    id: standard
    plugins:
      - id: tool-git
        name: '@deepseek-ai/dsh-tool-git'
        disabled: true  # <--- This completely strips the tool from the model's schema loop
  ```

- Caveat attached to it: target the tool config **inside the active preset block** or it is treated as a
  silent no-op. The assistant also warns a plugin removal is all-or-nothing, hence the guard approach.
- Third-party context cited: a "Mirage" DSH plugin whose bundle "disables the standard filesystem and bash
  sandbox providers, then inserts Mirage-backed implementations" — i.e. the fs/shell seams are swappable.

## 2. Tool-call interception — the `tools/pre-execute` hook (claimed, partly suspect)

- Core claim: every tool call passes an extensible allow/deny guard layer **before** the local tool
  executes, so git can be blocked at the tool-call level rather than by training or by shell tricks.
- **Suspect:** two different registration syntaxes appear and are never reconciled —
  `ctx.tools.on('tools/pre-execute', (callContext) => {…})` (earlier turns) and
  `ctx.on('tools/pre-execute', async (callContext) => {…})` (later turns).
- Call-context fields used: `callContext.name`, `callContext.args.command`, `callContext.args.text`,
  `callContext.args.path`.
- **Suspect:** tool names used for matching are `execute_bash`, `terminal_write`, `git_commit`,
  `git_clone`, and "any name starting with `git_`". None were checked against the harness.
- **Suspect:** `callContext.bypass((_args) => ({ stdout, stderr, code }))` — the silent-layer API. It
  appears only in the proposal the user rejected, and no source was cited for it.
- Error-feedback claim: a `throw` from the hook puts the message string directly into the model's context
  as tool-failure feedback, so a model can read "use this exact command instead: …" and re-issue the call.
  Framed as especially effective for "DeepSeek R1/V4" reasoning loops. This is the mechanism the whole
  design rests on, and it was never tested.
- Supporting claim from a third-party repo (`lxj808624/dsh-tool-git`): that tool executes arguments as an
  explicit array via `execFile` — "no shell injection: every command goes through execFile with an explicit
  argument array" — so checking `callContext.name` plus the `execute_bash` string gives full isolation.

## 3. Decision: a loud guard, not a silent translation layer

The only settled design decision in the thread, reached through an explicit user correction.

- **Rejected — silent translation.** The assistant proposed intercepting `git`/`bash`, faking a successful
  git result, and letting the model believe it ran git. Sample fake payloads:
  `stdout: "* main\n  main"`; `stdout: "Switched to a new branch '<branch>'"`;
  `stdout: "[<branch> <7 hex chars>] update jiu-jitsu structural matrix\n 1 file changed, 12 insertions(+)"`.
  Rationale offered: zero exposure, no error noise. The user rejected it outright.
- **Adopted — loud structural boundary.** The hook terminates the call, states the constraint, and maps the
  intended action to a mandated command the model must run instead. Rationale in-thread: keeps the system
  "clean, visible, and totally trackable without any magic proxies", and forces the model to reason about
  the restriction and self-correct.
- Final guard message template (earlier variants `GIT EXECUTION BLOCKED.`, `[PROJECT-LOCK] …`,
  `[SANDBOX ALERT] …` are **superseded**):

  ```
  [SECURITY POLICY VIOLATION]
  Workspace Status: Jiu-Jitsu Domain Detected.
  Constraint: Direct Git operations are strictly disabled.
  Static Routing Action: Execute the following platform command to perform your intended modifications: `<cmd>`
  ```

- Detection is deliberately overt: check for a signature file rather than masking payloads
  (`await ctx.fs.exists('/jiujitsu.config.json')`).

## 4. Conditional project detection (claimed)

- The guard must be scoped to one repository, not global, so it silently drops out of the lifecycle loop
  elsewhere. Detection signals proposed, in order of preference:
  - `ctx.fs.exists('/jiujitsu.config.json')`
  - `ctx.fs.exists('/src/techniques')` (registry directory)
  - fallback: read `package.json` and match `pkg.name` against `jiujitsu` / `jiu-jitsu`
  - earlier, Node-based variant used `process.cwd()` + `fs.existsSync(path.join(projectRoot, …))`
- Explicitly flagged as unresolved: whether the rule applies to a monorepo folder only or to every folder
  the agent opens — the assistant asked twice and never got an answer.

## 5. Filesystem access: `ctx.fs` over `node:fs` (claimed)

- Rule stated: plugins should use the harness's packaged fs utilities (`ctx.fs`), never `node:fs` directly.
- Stated reasons:
  1. **Pluggable backends** — `fs-local`, `fs-sandbox`, or a virtualized overlay (Mirage). Importing
     `node:fs` escapes the configured sandbox and exposes the real disk.
  2. **Policy enforcement layer** — `fs/write-intent`, `fs/edit-intent` and the `fs-observation-policy`
     package track read-before-edit validity; going through `ctx.fs` lets other plugins enforce bounds.
  3. **Structured errors** — `ctx.fs` normalizes failures into typed `FsError` schemas with predictable
     error codes the model loop can read and recover from.
- Usage shown: `await ctx.fs.readText('/sandbox/jiujitsu-core/positions.json')` inside `ctx.on('ready', …)`;
  `ctx.fs.exists(...)`, `ctx.fs.writeText(...)` used elsewhere.
- Package note quoted from the docs: `deepseek-ai/dsh-fs` — "You rarely load dsh-fs directly: you mount a
  backend that registers as `ctx.fs`". For model-facing commands, the thread points at `defineTool` from
  `@deepseek-ai/dsh-tools`.

## 6. Bash execution and sandboxing (claimed)

- Position: DSH **does not** simulate bash in memory. It runs real bash commands inside a restrictive
  process-level sandbox.
- Claimed seam and modules:
  - `ctx.shell` — modular shell executor layer.
  - `dsh-bash-local` — commands as fresh, raw `bash -c` subprocesses with the user's permissions.
  - `dsh-bash-sandbox` (**default mode**) — real bash trapped by the OS: Linux bubblewrap (`bwrap`) /
    Landlock, macOS Seatbelt, Windows ACL restricted tokens.
- Every execution is interceptable *before* the platform runner spawns the OS process, whether via the
  one-shot `dsh-tool-bash` or the stateful `dsh-terminal-bash`.
- Quoted doc line: "On POSIX, dsh-bash-local runs commands as fresh `bash -c` processes and
  dsh-bash-sandbox confines every command through the sandbox".
- Confinement boundary named: `workspace-write`.
- Flagged: one citation in this turn was an unattributed "CVE-2026" snippet about an agent holding a
  shell. No CVE id, no detail — treat as unsubstantiated noise.

## 9. Jujutsu: hunk-level operations and `jj-hunk`

- A **hunk** = a contiguous block of modified lines inside a file's diff.
- Native `jj` rewrites history at commit/file level (`jj split`, `jj squash`), but isolating individual
  hunks or lines forces the **interactive diff editor** (`jj split -i`). That TUI requirement is the
  roadblock for headless agents.
- `jj-hunk` (also referred to as `jj-hunk-tool`; upstream project `laulauland/jj-hunk`, described as
  "Non-interactive hunk distribution in jj CLI", published on crates/lib.rs and as a Smithery skill) is the
  CLI bridge that bypasses the TUI.
- Commands attributed to it:
  - `jj-hunk split` — non-interactive splitting of working-copy (`@`) changes into discrete commits.
  - `jj-hunk squash` — merge targeted hunks into designated parent/ancestor revisions, ignoring other
    changes in the same file.
  - `jj-hunk list` — "List hunks, files, or spec templates"; diffs a revision against its parent and
    exports it.
  - `--format json|yaml|text` — output format selector (default `text`), letting a plugin statically
    inspect the payload.
- **Suspect:** the claim that `jj-hunk` "assigns stable IDs to each patch chunk" was asserted but never
  demonstrated; no id syntax or example output appears anywhere in the thread.
- Intended use: let the DSH plugin inspect the structured hunk payload to decide routing rules, and let an
  agent isolate/version domain data inside the sandbox. Also proposed for pre-push CODEOWNERS verification.

## 10. Jujutsu → GitHub: bookmarks, push, force semantics

- `jj` operates natively on a Git backend and pushes upstream to GitHub; it tracks changes by **Change IDs**
  rather than branch pointers.
- GitHub needs named refs, so `jj` uses **Bookmarks**:

  ```bash
  # 1. Attach a named bookmark to your current working revision (@)
  jj bookmark create my-feature-branch -r @

  # 2. Push the bookmark up to your GitHub remote
  jj git push --bookmark my-feature-branch
  ```

- Quick PR path: `jj git push -c @` auto-creates a randomized bookmark and pushes it, then prints the
  standard GitHub PR-creation link. Example generated name given: `push-sytrsqlnznzr`.
- Multi-remote (fork vs upstream), set via `jj config edit`:

  ```toml
  [git]
  fetch = "upstream"
  push = "origin"
  ```

  Then `jj git fetch` pulls from the org and `jj git push` targets the fork.
- Force semantics: because `jj squash` / `jj amend` / `jj rebase` rewrite commits, `jj git push` behaves
  like `git push --force-with-lease` — it updates an existing PR branch while running safety checks.
- Cheat-sheet variants cited: `jj git push -b main` (older spelling, alongside the modern
  `jj git push --bookmark`), and rebasing a chain with `jj rebase -r new-feature -d main`.
- Core command surface listed in a cited tutorial: `new`, `describe`, `commit`, `prev`, `next`, `squash`,
  `rebase`, `abandon`, `fix`, `absorb`, `bisect`.
- Authentication for `gh` was raised as a question and never answered.

## 11. `jj git init`, configuration, nested forks, unsupported Git features

- `jj git init` works and, in modern versions, creates a **colocated workspace** by default: `.jj` and
  `.git` sit in the same root, so git-native tooling and GitHub Actions keep working. Cited version detail:
  "In jj 0.42 and 0.43, `jj git init` is colocated by default (`--no-colocate` opts out), so most jj repos
  an agent meets are colocated."
- Recommended follow-ups after init:
  - `jj bookmark track main@origin` — explicit upstream tracking so local work rebases automatically.
  - `[git] fetch`/`push` mapping in `~/.config/jj/config.toml` (global) as in §10.
  - `jj git export` — "Pushes current jj state into the local `.git` directory", needed before tools that
    read standard git refs, e.g. `gh pr create`.
- **Nested-fork bottleneck (claimed):** `jj git fetch` imports *every* reference into the operation store
  (`op store`), so hundreds of forks/parent repos cause command-line slowdowns. Fix — narrow the fetch
  patterns:

  ```toml
  [git]
  fetch = ["refs/heads/main", "refs/tags/*"]
  ```

- **Worktrees:** Git's `git-worktree` is explicitly unsupported by the jj backend. Use jj workspaces
  instead: `jj workspace add ../nested-fork-feature` (distinct working directory, same repository storage).
- **Sparse checkout:** jj does **not** support Git's sparse-checkout engine or partial blob clones
  (`--filter=blob:none`). Use jj's own sparse system, which keeps patterns in the `.jj` metadata store:
  `jj sparse set --minus "path/to/heavy-nested-directories"`.
- Cited Git-compatibility list — **unsupported**: `.gitattributes` (No), hooks (No), submodules (No),
  partial clones (No), `git-worktree` (No), sparse… (the source snippet is truncated at "Spa…"). Recorded as
  cited-but-incomplete; the "No" for `.gitattributes` is questionable and unverified.

## 12. Workflow compatibility (claimed)

**AI coding assistants and editors (Cursor, Copilot, Trae).** In a colocated workspace the editor sees a
normal git working directory and normal modified-file status. Failure mode: an editor's "commit" button or
an agent auto-generating a commit message will call `git commit`, which a hard harness-level git guard
breaks. Fix: have agents run `jj commit -m "..."`, or rely on jj's automatic working-copy commits (every
file modification is instantly recorded into `@` with no explicit command).

**pnpm monorepos and Turborepo.** Turborepo decides changed packages and cache reuse from git hashes
(`git diff`). Because jj does not export every change into the local `.git` ref map instantly, cache
pipelines can break. Fix: run `jj git export` on a file-watch hook, or prepend it:

```bash
jj git export && pnpm build
```

Lockfile churn: switching between change pathways changes the working directory instantly via the
anonymous-commit system, so a shared `pnpm-lock.yaml` can look permanently out of sync unless package
changes are committed to a stable parent revision.

**CI/CD and stacked PRs.** The thread's table:

| Step | Traditional Git | Jujutsu |
| --- | --- | --- |
| Dependency updates | manual conflict management across feature branches | concurrent change IDs rebase automatically when `main` updates |
| Creating a chain | `git checkout -b feature2` off `feature1`, manual parent tracking | create a new commit over an existing change ID (`jj new`) |
| Submitting PRs | push separate branch names, link them in the GitHub UI | `jj git push -c <rev>` pushes individual commits as distinct PRs |

- GitHub Actions only trigger when a **named ref** changes. Local experimental jj commits create no branch
  until a bookmark is attached, so changes stay sandboxed locally until deliberately exported.
- After a bot merges a PR, `jj git fetch` pulls the update and jj automatically rebases local stacked
  changes onto the new upstream head (no manual conflict cycle claimed).

**Code review.** When a reviewer requests changes, skip checkout+fixup+squash: `jj edit <change_id>`, edit
in place, `jj git push` — jj updates the existing tracking bookmark and the PR file tree. For repos with a
`CODEOWNERS` layout, the thread suggests using `jj hunk` parsing locally to verify line-by-line ownership
before pushing a bookmark. (Note: spelled `jj hunk` here, `jj-hunk` elsewhere — same tool.)

## 13. Jujutsu semantics: how `git commit` and `git branch` map

- **No staging area.** Every file edit is auto-recorded into the open-ended working-copy revision `@`;
  there is no `git add`. `jj new` closes the current change and starts a fresh empty working copy on top.
- **Two identifiers per revision:**
  - **Change ID** — permanent, stable across rewrites.
  - **Commit ID** — cryptographic hash (git-commit equivalent) that changes whenever contents change.
- **Branches are anonymous by default.** A new line of history is just `jj new <commit_id>`; naming is
  optional. **Bookmarks** are the named labels that translate to git branches.
- **Bidirectional sync in a colocated workspace:** `jj bookmark create my-feature` instantly exports a
  branch ref into `.git`; conversely, a `git branch` switch done by another tool is picked up by jj on its
  next execution, which updates the active `@` indicator to match.

| Operation | Git | Jujutsu |
| --- | --- | --- |
| Save modifications | `git add` then `git commit` | automatic — every save updates `@` |
| Start a new task | `git checkout -b feature-name` | `jj new` (naming optional) |
| Rewrite/amend earlier work | `git commit --amend`, interactive rebase | `jj squash`, `jj edit <change_id>` |
| Prepare for remote push | push a local branch name | `jj bookmark create <name>` then `jj git push` |
